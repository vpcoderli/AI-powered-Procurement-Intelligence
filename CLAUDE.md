## Project Overview

APSi (AI-powered Procurement Intelligence) is a monorepo with two subsystems:

- **`frontend/`** — Full-stack Next.js 15 app (TypeScript, React 19, Tailwind CSS v4, shadcn/ui, Drizzle ORM). Serves the web UI and all API routes. Also contains background worker scripts.
- **`crawler/`** — Python-based bid aggregation engine with 50+ state portal scrapers and a SAM.gov adapter.

The frontend is the primary active subsystem. The crawler runs as a separate process and writes directly to the shared database.

## Frontend Commands

All commands run from the `frontend/` directory.

```bash
npm run dev                      # Start Next.js dev server (localhost:3000)
npm run build && npm run start   # Production build
npm run lint                     # ESLint
npm run test                     # Run Vitest test suite
npm run db:migrate               # Apply SQLite schema migrations
npm run db:seed                  # Seed demo data
npm run auth:reset-admin         # Reset admin password
STATE_CRAWLER_LIMIT=5 npm run crawler:once   # One-shot crawler run (limit sources)
npm run worker:crawler           # Continuous crawler background daemon
npm run worker:events            # Event processing daemon
npm run worker:notifications     # Notification delivery daemon
npm run workers:check            # Health check all workers (non-blocking)
npm run source:health:check      # Verify scraper source liveness
npm run billing:stripe:sandbox   # Stripe E2E sandbox test
npm run risk:check               # Data/entitlement risk gate (also runs in CI)
```

To run a single Vitest test file:
```bash
cd frontend && npx vitest run src/path/to/file.test.ts
```

### Docker / CI

```bash
docker compose up --build        # Build and run the web app locally (repo root), http://localhost:3000
docker build -t apsi-frontend frontend   # Build the production image directly
```

`.github/workflows/ci.yml` runs on every push/PR: `npm ci`, `lint`, `test`, `build`, then seeds a throwaway SQLite DB (`npm run db:seed`) and runs `npm run risk:check` as a merge gate. `frontend/Dockerfile` is a multi-stage build (`deps` → `builder` → `runner`) using Next.js `output: "standalone"` (see `frontend/next.config.ts`) and only packages the web process — the three worker scripts are not included in this image (see comments in `frontend/Dockerfile`). `docker-compose.yml` at the repo root is for local/demo parity only; it does not represent the production topology documented in `docs/operations/aws-deployment-runbook.md`.

## Architecture

### Database

- **Local/dev:** SQLite at `frontend/data/apsi.sqlite` (default, zero config)
- **Production:** MySQL via `DATABASE_URL` env var
- **ORM:** Drizzle ORM — schema lives in `frontend/src/server/db/schema.ts`
- **Migrations:** `frontend/drizzle/` — generated by drizzle-kit, applied with `npm run db:migrate`

The database has 30+ tables covering: bids, users/auth, intents (bidding workspaces), response workspace items, artifacts, quotes, notifications, billing/subscriptions, crawler state, and source health.

### Frontend Structure

`frontend/src/app/` uses Next.js App Router. Key routes:
- `/search` — primary bid search interface
- `/bids/[id]` — bid detail
- `/intents/[id]` — intent/bidding workspace
- `/saved` — user favorites
- `/knowledge` — knowledge base
- `/settings` — billing & preferences
- `/admin` — crawler status and source health (admin only)
- `/api/*` — server-side API routes (all data access goes through here)

`frontend/src/server/` contains server-only code: DB queries, billing logic, notification dispatch, and auth helpers.

`frontend/src/components/` — UI components. Business components are co-located with feature modules; base UI components (shadcn wrappers) are in `components/ui/`.

`frontend/src/lib/` — utilities, i18n dictionaries (en/zh), type definitions.

### Crawler Architecture

`crawler/apsi_crawler/spiders/` — one spider per state portal. `generic_state.py` is the base class. Spiders output normalized `BidRecord` objects via the normalizer layer before writing to the database.

### Workers

Three long-running worker scripts in `frontend/scripts/`:
- `crawler-worker.ts` — periodically invokes state crawlers
- `event-worker.ts` — processes the outbox event queue (triggers downstream effects)
- `notification-worker.ts` — delivers pending notifications via configured provider

### Auth & Billing

- Auth: custom session-based auth (no NextAuth). Session cookies, password reset via email.
- Billing: Stripe integration with webhook handler at `/api/billing/webhook`. Subscription tiers: Free, Pro, Business. `BILLING_PROVIDER=local` disables billing in dev.

## Environment Variables

Create `frontend/.env.local` for local dev. Key variables:

| Variable | Dev default | Notes |
|---|---|---|
| `DATABASE_PATH` | `data/apsi.sqlite` | SQLite path relative to `frontend/` |
| `DATABASE_URL` | — | MySQL URL; activates MySQL mode |
| `ADMIN_UI_LOCAL_BYPASS` | `true` | Skip admin auth locally |
| `BILLING_PROVIDER` | `local` | Use `stripe` for billing tests |
| `STRIPE_SECRET_KEY` | `sk_test_REPLACE_ME` | Stripe test key |
| `STRIPE_WEBHOOK_SECRET` | `whsec_REPLACE_ME` | Stripe webhook signing secret |
| `NOTIFICATION_PROVIDER` | `file` or `console` | `http` for real delivery |
| `SAM_API_KEY` | — | For SAM.gov federal bid crawling |

Full variable reference: `docs/transferability/environment-variables.md`
