# 来源与招标链路的 module 深化

依据：2026-10-08 架构报告；用户已要求按四个建议整理任务并实施优化。保留当前分支的所有既有修复，不部署、不写业务数据库、不触发线上采集。

## 1. 平台采集轮次

平台采集轮次 module 拥有一次 tick 的预算、时间线和工作顺序。列表、预检、正文补采是真实 adapter；worker 调用完整轮次，而不自行重建多个时间线。每次网络失败后的重试也必须计费；已成功入库不重试；没有联系来源的 blocked/locked/deferred/disabled 不计请求。不报告请求数量的已开始尝试采用保守成本，不能把未知当零。额度耗尽后停止追加尝试，保留最后真实失败结果，不把预算跳过改写为源成功。

列表→预检共享最小间隔和暂停；正文补采使用剩余额度并排在预检后，默认关闭。继续使用单 worker、现有源租约、暂停内存语义和公开网页限制。独立运行入口可保留兼容行为；worker 的完整 tick 是跨步骤测试的 interface。

## 2. 招标接纳

一个招标接纳 module 拥有候选门禁、旧身份保护、正文/附件有效合并、质量账、完整范围下架和运行日志的共同顺序。SQLite/MySQL adapter 只拥有真实数据库差异和事务连接操作，不再各自复制领域编排。兼容现有 importer 调用；提交后才公布 metadata，失败必须回滚，失败日志尽力留存。

保留 SQLite immediate 事务、MySQL 提交前短时锁租约行、单连接池失败时先归还连接再写日志。Python 独立 CLI 的契约保持，不引入跨语言远程调用。已有 merge/quality implementation 保留为内部 module。

检查中确认失败日志存在相关完整性问题：事务回滚后的直接日志路径会沿用输入的 `metadata.dataQuality`。如果它是格式和核对关系均有效的旧成功质量账，报告可把未提交批次显示为“可用”；格式不合格的账本原本已被拒绝。本项同时要求重新生成失败质量账，接纳数为零、执行失败、内容状态未知；原候选数保存在 `persistence.fetchedBeforePersistence`。不修改失败调用的原 payload metadata。

## 3. 手动抓取执行

一个浏览器可用的手动抓取 module 拥有来源映射、顺序分块、日期窗口转换、逐来源结果和部分完成。单源详情、来源列表、辖区运行保留选择、确认、刷新和展示，消费同一执行 interface。state/manual 与 SAM 是真实 adapter；结果解释不再从视图 module 反向导入。

保留每批 5 个、来源列表选择上限和现有权限；列表发送失败后停止、辖区批次发送失败后继续的差异显式保留。不更改预检、审批等其他写操作。不以源码字符串检查代替完整异步执行行为。

部分完成的结果应区分已确认返回、请求传输失败和尚未发送。列表传输失败后保留此前已确认批次的 tally，未发送任务不冒充已执行。成功响应中的缺项最终标为 unknown，不能留在 running；来源的结构化失败不等同于传输失败，不应因此偷偷改变后续批次策略。

已用真实 mapper 复现本地来源的相关错配：登记 `id=city_portal`、`jurisdictionLevel=city`，旧 `issuerType=state` 和由它生成的 `crawlerSourceId=il_bidbuy` 时，手动运行目标变成州门户。共同 mapper 应以明确登记的 jurisdictionLevel 为准，本地来源通过自身 data_sources ID 运行，联邦不进入 state route，州来源保留旧 alias 兼容。补测覆盖县、市、乡镇和特别区的广义旧类型。

## 4. 来源身份

共享来源身份 module 集中实际字段归一化、canonical ID 优先和注册来源一致性。导入、正文补采、报告和用户读取通过该 module 判断。共同规则与场景限制分开：导入 namespace、稳定编号补采、未注册历史行兼容和歧义 label 处理保持现有语义。

不新增全局完整分数，不提高可选字段要求。发现、分析和附件继续按实际用途门禁。

继续核查时用真实招标接纳 interface 复现 namespace 漏检：候选 `id` 为空、`dedupe_key=other_portal:one`，而本次登记来源为 `city_portal` 时，现有门禁先检查空 ID，再用 dedupe key 生成 ID，最终错误接纳为 `other_portal:one`。身份门禁必须检查将实际使用的派生 ID；错误 namespace 隔离且不触发完整范围下架。保留合法缺 ID 回退、可选字段和未注册历史行兼容，不提高普通核心门禁要求。

组合核查又确认去重后的实际目标也必须检查：候选 `id=city_portal:one` 虽然符合登记来源，但 `dedupe_key=other_portal:one` 命中另一来源旧记录时，接纳 workflow 会选择旧主键并覆盖对方正文，质量账仍允许下架。第 4 项因此同时检查去重后实际保存的 ID，必须在读取附件或写入之前隔离越界目标。相同来源的实际存储 ID 合并、非 namespaced 旧 ID 兼容和无登记 metadata 的旧路径保持；不能只检查输入 ID。

## 验收

两处组合反例必须先 RED 后 GREEN：预算 3 下两次请求只余 1；列表切到预检仍等待最小间隔。两数据库接纳的原子性、租约与下架反例通过；三个手动入口不再拥有执行循环；四个身份 caller 保持场景契约。最终执行全量前端、爬虫、解析、下载和独立 MySQL 集成、Lint、生产构建，以及类型诊断相对本轮基线的差异检查。
