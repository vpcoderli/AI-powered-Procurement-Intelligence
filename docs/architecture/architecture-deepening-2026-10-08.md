## 报告结论与优先级

数据完整性首先依赖两个可验证的事实：采集执行受到统一控制，接纳结果与实际保存内容一致。HTTP 成功只能证明请求完成；列表覆盖、正文可分析和附件可下载分别需要证据。未取得证据的内容应明确为部分完成、待补采或隔离，不能显示为完整可用。

原报告将平台采集轮次和招标接纳评为 Strong，将手动抓取执行和来源身份评为 Worth exploring。前者已有可复现的组合缺陷，优先修复；后者基于多个 caller 重复解释同一规则的维护摩擦，随后通过完整行为契约深化。

| 报告发现 | 影响 | 优化目标 |
| --- | --- | --- |
| 重试执行与预算结算分开，仅观察最终一次请求；列表和预检另建时间线 | 实际请求漏计，同平台跨步骤等待失效 | 一次轮次拥有逐次结算、间隔、暂停及优先级 |
| 两个 importer 复制门禁、有效合并、附件、下架与日志顺序 | 同一数据完整性修复需要修改两个流程，容易分歧 | 一处招标接纳 workflow，数据库 adapter 保留事务差异 |
| 三个手动入口各自组合分块、窗口、状态与部分成功 | 缺项响应可留下“运行中”，状态修复容易只覆盖一个入口 | 一处执行 interface，明确保留停止/继续策略 |
| 导入、补采、质量报告与用户读取各自解释来源身份 | 字段映射与归属判断分散，历史兼容规则难以核对 | 一处身份 policy，场景附加约束显式保留 |

“每次数据都可用”的工程保证应落实为：每批均有核对账，每条均有用途能力，失败可定位与补采，旧的有效内容不因劣质重导入丢失。源站遗漏、拒绝访问或内容未公开无法由架构消除，因此本轮验收检查真实状态和门禁，不将网络返回成功当成完整性保证。

## 数据完整性的验收口径

| 层次 | 必须取得的证据 | 未满足时的处理 |
| --- | --- | --- |
| 执行与覆盖 | 真实执行结果、分页范围、请求成本；完整列表或来源范围的 verified empty | 明确失败/部分/未知；范围受限的结果不下架缺席记录 |
| 候选与身份 | 唯一候选数等于接纳加隔离；派生 ID、登记辖区和稳定身份一致 | 隔离并保留脱敏证据；禁止错误来源覆盖旧记录 |
| 正文 | 有效正文及选中内容的实际验证时间、是否复用 | 可发现但不冒充可分析；保持旧有效正文并进入补采 |
| 附件 | 保存字节、大小、校验和和实际验证记录 | 链接可保留；未经验证的归档不冒充可下载 |
| 提交与报告 | SQLite/MySQL 原子提交、日志与提交后的质量账一致 | 回滚；失败账接纳数为零，不能沿用上游成功账 |
| 管理操作 | 每个请求目标有最终状态，已返回、传输失败、未发送可区分 | 保留部分完成证据；缺项标未知，避免长期显示运行中 |

这张表是本轮回归的验收依据。完整覆盖与内容能力分别核对，不合并成一个无法解释的“完整率”。

## 设计取舍

来源身份检查还复现了一个数据完整性反例：空 ID 的候选在校验后才由 dedupe key 派生实际 ID，可绕过来源 namespace 检查，进入其他来源的 ID 空间。第 4 项将门禁对准实际派生 ID，并验证隔离后不会下架旧有效记录。

输入 ID 符合来源时，错误去重键仍可能让 workflow 选中另一来源旧主键。控制者用真实接纳 interface 复现了跨来源正文覆盖和允许下架，第 4 项补查实际保存目标，在附件读取及写入前隔离。有效的同来源去重规则继续保留。

保留已有有 depth 的 merge、quality、budget、retry implementation。深化的目标是减少 caller 必须理解的 interface 事实，并使 tests 与 caller 通过同一 seam。SQLite/MySQL、列表/预检/正文补采、state/SAM 都是已存在的真实 adapter，避免为假想变化添加框架。

保留单 worker、源租约和入库 fencing、暂停内存语义、抓取与私有解析/browser 进程分离、公开页面访问限制、历史补采默认关闭、管理端角色守卫和单导航。不新增业务表、迁移、队列或全局状态库。

详细设计见 [设计稿](../superpowers/specs/2026-10-08-architecture-deepening-design.md)，逐项测试与执行清单见 [任务清单](../superpowers/plans/2026-10-08-architecture-deepening.md)。领域术语见根目录 `GLOSSARY.md`。

## 平台采集轮次的实施结果

`frontend/src/server/crawler/worker-tick.ts` 的 `createCrawlerWorkerTick(options, adapters?)` 创建完整 tick interface。module 拥有每轮预算、共享时间线、列表→预检→正文补采排序，以及 worker 生命周期的暂停和预检重试状态；worker 仅消费阶段结果并记录日志。

每次实际重试独立预留和结算，额度耗尽返回最后真实失败；未知成本保留预留量，未联系的跳过项退回额度。请求成本采用报告的 `pagination.requests_made`，缺失或格式错误不能当零；它不证明未报告的其他 HTTP 工作的精确总数。停止信号在间隔等待期间到达时，新增联系被阻止，未使用预留退回。

## 招标接纳的实施结果

`frontend/src/server/crawler/bid-intake.ts` 通过同一 workflow 提供同步与异步 interface。SQLite/MySQL adapter 只实现六项招标专用存储操作及事务/租约机制；身份保护、有效正文与附件快照、质量能力、候选核对、下架和完成日志顺序均由共同 module 拥有。payload/result 类型仍从原 MySQL 路径兼容导出。

新增修复：回滚日志不能继承格式有效的旧“可用”质量账。`persistenceFailurePayload` 重新生成失败质量证据，执行失败、内容未知、接纳/正文/分析数为零；候选数仍保存在失败前证据中，原 payload metadata 不变。真实 SQLite 接纳→报告测试验证报告结果与保留下来的旧好数据一致。

目标回归 132 项通过，需求与代码质量独立复审均通过。Node 20 的 Python→HTTP 解析→SQLite/MySQL 独立链路 2 个套件、26 项通过，含新增的实际存储 ID、跨招标附件冲突回滚和附件字节验证场景。MySQL 使用单连接池和随机测试 schema。预先建立临时 SQLite WAL 文件后避免了测试并发首次初始化锁冲突。类型诊断仍为 276，无本轮新增。

## 手动抓取执行的实施结果

`frontend/src/lib/manual-crawl.ts` 的 `runManualCrawl(request, options)` 拥有来源映射、顺序五源分批、日期与 state/SAM 格式转换、逐源最终状态和部分完成。三个视图消费同一 interface；列表传输失败停止，辖区批次继续。已确认 tally 保留，已尝试和未发送区分，缺项响应最终为 unknown，非请求来源不会进入本次统计。通用审批/预检分块及兼容导出保留。

地方来源按明确登记辖区使用自身 ID，不能沿用旧广义 issuerType 派生的州 alias；联邦不进入州路由，州 alias 与旧缺失辖区回退保持。日期校验包含真实日历日期和规范化空格，UTC 范围包含首尾日。明确来源错误仍保留错误提示，与缺项未知区分。

需求复审通过真实 HTTP adapter 复现了 SAM 响应归属缺口并要求补修。当前仅接受 `source=sam_gov`、布尔 ok、合法且一致的 status 后归属；错误/缺失来源或矛盾成功标志返回裸 unknown，不继承错误来源的数量和原因。合法 HTTP 409 跳过与 500 执行失败保留结构化结果，权限及其他传输错误保持拒绝。新增 11 项 RED 反例后，目标回归 11 个套件、277 项通过；需求复审重审和随后代码质量复审均通过，类型诊断与本轮基线一致。

## 来源身份的实施结果

`frontend/src/lib/source-identity.ts` 集中字段归一化、非空字段比较、实际导入 ID 派生、来源命名空间校验及登记归属索引。导入、正文历史、用户读取和质量报告消费同一规则；稳定编号和名称保持大小写，辖区比较是否忽略大小写由场景明确选择。登记归属依次按 ID 前缀、精确来源编号、唯一名称判定，歧义不能推定归属。

用途差异继续显式保留：导入仅比较原有四个登记地理字段，并保护六个既有稳定/地理字段；正文历史要求原始 canonical ID 完全一致；用户读取保留未知历史来源的核心门禁兼容，质量报告将未知或歧义记为未归属。日志来源使用精确编号或唯一名称，不套用招标前缀规则。补采、报告快照及分页方式保持。

本项修复两处实际写入目标漏洞。门禁首先检查空 ID 的真实派生值，再在去重 lookup 后、读取附件前检查选中的存储主键。即使另一来源旧记录的核心字段有缺陷，也不能被当前来源“修复”覆盖。错误候选保留原始隔离证据，接纳数为零、范围降为部分，不允许下架；同来源去重、非命名空间旧 ID、无登记 metadata 等兼容行为通过回归。

跨来源去重的 7 项行为反例先失败后通过，覆盖同步/异步接纳及真实 SQLite。目标回归 12 个套件、259 项通过。控制者独立复现确认没有招标写入和下架调用；真实 MySQL 测试分别以有效、缺陷旧记录验证两个来源的招标和附件完整快照未变。修复后需求复审重新通过，随后代码质量复审通过，无待修发现。
