# 采集数据完整性与可用性保障方案

日期：2026-10-01。范围：当前工作区的联邦、州、郡、县级地方机构、市、镇及特殊辖区采集链路。

本文件保留修复前的保障方案与缺口快照，**不是线上数据完整率报告**。2026-10-01 后续已实施语义入库门禁、历史补采、全辖区质量报告及用户端用途约束；实现和验证状态见[全面修复记录](crawler-data-usability-fixes-2026-10-01.md)。离线回归不证明每轮线上内容完整；未修改业务数据库。

## 1. 验收目标

“每次数据可用”应落实为：每轮采集的范围和结果可解释；对外提供的记录满足其使用场景；不满足条件的记录有明确原因和补采路径；失败结果不会破坏已验证数据。

必须分别回答三个问题，不能用一个 `success` 代替：

| 维度 | 要回答的问题 | 建议状态 |
| --- | --- | --- |
| 执行结果 | 请求、解析和持久化是否正常完成？ | 成功 / 失败 / 延后 |
| 列表覆盖 | 指定来源、时间范围和列表类型内，是否有证据证明取全？ | 完整 / 部分 / 无法判定 |
| 单条可用性 | 当前记录能够支持检索、需求分析、文件下载中的哪些功能？ | 分别标记能力及待补字段；核心错误则隔离 |

例如：本轮取得 25 条列表，只有 20 条有效正文。若分页证据充分，列表可以是“完整”；正文覆盖是 20/25；余下 5 条是“可检索、正文待补”，不能报成 25 条分析可用，也不应丢掉这 5 条有效列表。此例为验收示例，不是当前线上测量。

外部站点不可控，无法承诺所有来源每次都返回全部字段。系统应承诺：**不把未知当完整、不把占位内容当有效、不把过期内容当刚验证、不把下载链接当真实文件。**

## 2. 当前实现具备的保障与主要缺口

| 方面 | 当前代码行为 | 对数据质量的影响 |
| --- | --- | --- |
| 来源身份 | 本次工作区已加强辖区类型、州/FIPS、租户和重复源校验 | 降低串源、错误归属和重复注册；仍需核验每个门户的真实业务范围 |
| 分页与下架 | BidNet 链路记录分页完整性；成功、完整的 open 列表才允许关闭未出现的旧记录 | 是已有的重要保护；不能推断所有适配器都已具备同等覆盖证明 |
| 详情补全 | 可选开启，默认每轮最多 25 条；服务不可用或单条失败保留列表 | 保住列表可用性，但列表成功不能代表正文成功 |
| 补全统计 | `enriched` 表示有字段写入，分类或联系人变化也可计数；`skipped` 混合多种情况 | 不能据此计算有效正文率，也难以逐条安排补采 |
| 入库校验 | `validateCrawlerImport` 检查数组形态及零条成功依据；导入器有占位值 | 已有结构与空态守卫，尚不是逐字段、按业务用途的语义发布门禁 |
| 源健康 | `result.ok` 即更新成功时间，未要求有效正文或附件通过 | 详情全失败时仍可能显示源采集成功；需要独立的数据质量状态 |
| 质量报告范围 | `state-data-quality.ts` 主要筛选 `issuerType === "state"` | 新增地方来源及联邦来源未被这一州质量报告统一覆盖 |
| 重导入 | 两种数据库共享正文/字段来源合并规则，保护已有详情和附件归档；事务与租约守卫防止部分写入 | 已保护部分好数据；仍需对所有拟更新关键字段做有效性与时效判定 |
| 附件 | 发现链接与下载归档分离；已有魔数、HTML 拒绝、校验和、复核和退避机制 | 有链接不等于能下载，更不等于文件与当前招标版本一致 |
| 补采公平性 | 通用详情及 SAM 从本轮列表顺序消耗预算，未利用持久化的缺失队列轮换 | 反复失败的前部记录可能消耗预算，后部记录长期得不到补全 |

## 3. 先建立每个来源的数据契约

来源契约应由平台适配器提供默认值，再由具体机构确认；不要求所有站点提供相同字段。契约包含：机构及辖区身份、列表类型、查询窗口、分页方式、可用总数依据、字段适用性、刷新频率、公开详情/附件能力、解析版本和验收策略版本。

“来源不提供”需要页面、API 契约或经过确认的站点样本支持。解析器没抓到字段，不能自动归类为来源不提供。

| 字段/对象 | 最低有效性要求 | 不满足时的处理 |
| --- | --- | --- |
| 身份 | 稳定的来源内编号，规范化来源身份；记录与租户/机构相符 | 禁止进入正式展示；保留原始候选行及定位信息供排查 |
| 标题/机构/辖区 | 真实标题，机构身份可核对，辖区来自已验证注册信息且与页面无冲突 | `Untitled`、`Unknown issuer` 等占位值不算通过；冲突隔离 |
| 原文定位 | 能定位该项目的详情页或可信 API 身份；允许经过证明的公开列表锚点 | 通用首页不能冒充项目详情；记录可用入口类型 |
| 正文 | 真实采购内容，非标题回显、导航、登录页、地址字符串或字段标签；保留来源 | 缺失时允许通过基础检索门禁，但禁止标记正文分析就绪；排队补全 |
| 日期/状态 | 日期可解析并保留时区/原始值；状态与已验证来源一致 | 无法解析、确实未提供与待获取分开；不根据模糊日期自动下架 |
| 联系人 | 来自对应联系字段，不能是 Purchase Method 等元数据；格式校验和来源说明 | 错位值清除或隔离该字段；没有联系人不必让整条记录失效 |
| 金额/分类 | 类型、币种、范围关系有效；分类匹配有来源或规则版本 | 不编造缺失预算，不把分类码当采购正文 |
| 附件 | 链接归属正确；实际下载后文件类型/大小/校验和有效，与采购项目关联 | 分别标记待下载、已验证、受限或失败；缺少文件时不宣称附件齐全 |

正文长短只能作为辅助信号。现有 150 字符等启发式不能变成统一硬门槛，合法的短采购说明也应通过语义检查。不能靠填充模板文字提高完整率。

## 4. 每轮采集执行六道校验

### G1：页面与来源真实性

- 校验 HTTP 结果、最终 URL、租户、预期页面身份及内容形态。
- HTTP 200 的登录页、WAF 页、错误页、空 JavaScript 壳不能算有效采购数据。
- 零条结果需要可信的空态证据，或明确过滤后零条的证据。超时、选择器失效或取错租户不能解释为“没有项目”。
- 保存可复放的最小证据：请求范围、必要响应元数据、内容摘要或受控样本、解析版本。不得在日志或证据中保存认证密钥。

### G2：列表覆盖与候选项对账

- 记录每页、游标、下一页、停止原因、总数依据及去重后的源内 ID 集合。
- 达到请求预算、页数上限、时间窗口或重复页时明确标为部分，不借用执行成功标记覆盖完整。
- 只有总数与实际采集范围一致、分页自然结束且身份一致时，才用可信上游总数计算覆盖率。
- 上游没有可信总数时，覆盖率为“无法计算”；可以记录已遍历到末页，但不能伪造 100%。分页过程中上游列表变化时也需保留不确定性。
- 无法解析身份的候选行也要保留行定位/内容摘要并进入隔离统计，避免在规范化阶段静默丢失。
- 部分或未知扫描禁止通过“本轮没出现”关闭旧记录。即使列表扫描完整，若部分候选行身份无法确认，仍禁止推断这些记录已下架。

### G3：单条语义校验与用途判定

建议将可用能力分别判定，避免强制分成互斥等级：

- **基础检索可用**：身份、标题、来源定位、机构辖区有效；允许正文、联系人等明确待补。
- **需求分析可用**：通过基础门禁，并有足够的有效正文或经过验证的采购文件文本；缺失信息不得由模型猜测。
- **附件可用**：具体文件已下载、验证并可读取。只有核对来源文件清单后，才能进一步声称该项目公开附件齐全。
- **隔离**：身份冲突、串源、必需字段占位、无法定位来源等核心错误。仅在管理端可排查，不进入正式数据流。

客户展示、搜索提醒和分析入口应使用各自用途的门禁。基础检索可用不代表适合用于自动分析或投标准备。

### G4：合并、事务与版本保护

- 新结果先完成质量判定，再决定哪些字段能更新正式记录；支持逐条接受，问题记录隔离。
- 空值、标题回显、错误页面和字段错位不能覆盖旧的有效内容。
- 来源明确修改截止时间、状态或撤回文件时，允许经证据验证的合法更新；不能把“保留旧值”变成永久冻结。
- 保留字段来源、观察时间、最后验证时间、来源版本或内容校验和。重用旧正文时仍使用旧的验证时间。
- SQLite/MySQL 使用同一质量规则；正式写入、质量判定结果及本次记录关联保持事务一致，租约丢失时回滚。
- 重跑相同输入应幂等，不新增重复机会、附件或重复提醒。

### G5：入库后的实际可用验证

- 按本轮 ID 清单核对写入结果，不能只看 `insertedCount + updatedCount`：同一个 ID 在输入重复出现会重复计操作次数。
- 验证记录读回后的关键字段、类型、来源和质量标记；确认数据库截断或序列化未损坏内容。
- 用风险分层样本检查搜索、辖区过滤、详情正文选择、权限和附件下载入口。新来源、新解析版本及出现异常的来源提高样本量。
- 全量自动检查轻量的记录约束；真实门户探测及大文件复核使用请求预算和刷新策略，避免每轮重复下载全部附件。

### G6：补采、监控与关闭问题

- 使用持久化的逐记录/逐字段任务队列，记录失败原因、次数、下次重试时间和最早等待时间。
- 区分未尝试、预算延后、服务不可用、网络失败、限流、解析失败、来源未提供及公开访问受限。
- 在缺失、发生变更、临近截止和已过期记录之间安排优先级，同时设置等待上限，避免队尾饥饿；遵守平台限流。
- 补采通过后重新计算能力与质量，形成可审计的状态转移。人工确认“来源不提供”要记录依据。
- 实时状态正常并不解除原批次的问题：原失败 ID 需补全成功、确认来源限制或人工结案。

## 5. 每轮必须留下的质量账单

建议最小结构如下，全部为待新增或待扩展的设计，不代表当前数据表已有这些字段：

| 层级 | 最小记录 |
| --- | --- |
| 来源/运行 | run ID、source ID、辖区类型、机构身份、请求窗口与列表类型、开始/结束、策略/解析版本、执行结果、分页覆盖、停止原因、可信上游数量 |
| 候选/记录 | 原始候选数量、有效唯一 ID 数、输入重复数、身份不明的候选数、接受/隔离/明确排除清单；与最终数据库 ID 的关联 |
| 字段 | 本轮有效值、缺失原因、适用性依据、字段来源与验证时间、是否重用旧值、是否过期 |
| 详情 | 待补数、实际尝试数、本轮有效正文数、解析/网络失败、预算延后、服务不可用；不要用 `enriched` 替代 |
| 附件 | 发现的项目文件数、已下载数、验证通过数、失效数、受限数、最近复核与文件版本 |
| 发布 | 检索可用数、分析可用数、已验证附件数、隔离数、保留旧快照数、读后校验结果 |

数据账应使用互斥分类。例如，对具有有效身份且属于本轮范围的去重记录：

`观察到的唯一 ID 数 = 接受进入正式数据的 ID 数 + 隔离的 ID 数`

明确过滤排除的 ID 另列；原始候选行、跨页重复及缺失身份的候选也另列，不能混入这个等式。以 ID 清单对账，不能仅凭总数相等判定无遗漏。部分批次只能核对已经观察到的对象，不能据此证明没观察到的对象不存在。

## 6. 关键指标与告警

所有指标应按**具体来源、辖区类型、平台适配器及时间**拆分；全国平均值容易掩盖单个郡、市的长期失败。

| 指标 | 口径 | 处理原则 |
| --- | --- | --- |
| 列表覆盖率 | 相同范围内，采集到的唯一 ID / 可信上游唯一 ID 总数 | 无可信分母记 N/A；缺页不显示完整 |
| 发布基础有效率 | 通过核心字段门禁的正式记录 / 对外正式记录 | 应为 100%；发现核心错误立即隔离相关数据并排查 |
| 正文覆盖率 | 有有效正文的记录 / 按来源契约应有正文的记录 | 同时报告本轮新获取与重用旧正文，重用值受时效门禁约束 |
| 本轮正文获取率 | 本轮获取到有效正文的记录 / 本轮实际尝试正文的记录 | 与待补量、预算延后量并列，不能靠减少尝试量制造高成功率 |
| 附件验证率 | 验证通过的当前项目文件 / 已确认的应有公开项目文件 | 无完整文件清单时只报已发现/已验证数，不宣称附件齐全 |
| 新鲜度 | 距离字段/列表最后有效验证的时间 | 按来源更新频率与字段变化风险设 SLA，不能用 DB `updatedAt` 代替 |
| 补采积压 | 等待数量、最老等待时间、连续失败和到期超时数量 | 必须跟踪队尾是否获得尝试；按来源契约告警 |
| 数据变动 | 数量、字段空值、解析方法、页面形态与同类历史窗口的差异 | 异常触发复核，不能直接认定为源故障或真实项目减少 |

分母为零时输出 N/A 并说明原因，不输出 100%。真正不适用的字段可排除，但需要记录依据；获取失败不能从分母中随意删掉。

建议第一批硬门禁：核心身份错误不发布；错误页面不当正文；已验证附件不允许 HTML 假文件或校验失败；部分列表不推断下架；发布前后 ID 对账不能有未解释差异。

当来源契约确认应有正文且本轮发生获取/解析故障导致全部缺失时，立即标记内容质量异常；不能仍以源执行成功作为正常证据。覆盖率下降阈值、重试时限和字段新鲜度应基于来源契约及可比历史样本确定，不先拍定统一 95% 或固定若干天。

## 7. 必测场景与验收证据

| 测试组 | 重点故障/边界 | 验收证据 |
| --- | --- | --- |
| 来源身份 | 同平台错租户、跨辖区、同租户别名、错误州/FIPS、来源身份被修改 | 正确注册或明确隔离，无串源及重复正式记录 |
| 列表 | HTTP 200 登录/WAF/空壳、真空态、缺页、重复页、游标循环、页面数量变化、时间过滤、预算截断 | 覆盖状态和原因正确；不误下架；候选/ID 对账可解释 |
| 正文 | 标题回显、Description 标签、短但真实正文、页脚、联系人错位、空单元格、错项目详情、乱码/截断 | 按字段语义接受或拒绝；原始值与字段来源可复查 |
| 限流/依赖 | 429、超时、解析服务离线、最大详情预算、连续头部失败 | 列表保留但不冒充正文完整；逐条进入正确队列；后部不饿死 |
| 日期/版本 | 时区、日/月歧义、截止日期改变、取消/授标、部分扫描未出现、旧正文被重用 | 合法状态更新；不误报刚验证或自动推断缺失记录关闭 |
| 附件 | 200 HTML、过期链接、重定向错项目、会话下载、半文件、损坏、同名更新、来源已撤回 | 真实文件验证；失败原因明确；保留可审计旧版本而不标为当前齐全 |
| 持久化 | 双数据库、提交失败、租约丢失、并发重复运行、重导入、附件/正文保护 | 回滚正确，规则一致，幂等，对账无未知差异 |
| 用户端 | 搜索、辖区过滤、详情显示、提醒、分析入口、权限、真实下载 | 只有相应能力就绪的数据进入对应功能，缺失/过期状态可见 |

离线确定性回归验证故障处理；保存的真实 HTML/API 样本验证解析语义；隔离数据库验证事务与读回；有请求预算的线上核对验证当前门户和真实可用率。四类证据相互补充，不能用离线测试通过替代线上数据验收。

客户 MA/NJ/OR/PA 原批次应成为第一组线上验收对象：按原 ID 对比正文、联系人和文件清单，给出成功补齐、公开受限、来源无此字段或仍待修复的逐条结论。新来源需逐个通过首批人工核对；抽样按平台及辖区分层，不能只核查州来源。
